SQL注入

应用程序没有把用户的输入当成“数据”，而是直接拼成了“代码”，导致数据库把攻击者输入的恶意内容当成合法指令给执行了。

常见 SQL 注入

1、基础型 SQL 注入

直接将恶意 SQL 代码嵌入用户输入中，并影响查询逻辑。

2、UNION 查询注入

通过 UNION 将攻击者构造的查询结果与合法查询结果合并，从而获取敏感数据。

结果：将 users 表的 username 和 password 数据作为结果返回。

首先，union得保持前后两个select查询的列数相同，前三列（users）,id,name,后三列null,username,password，又因为id = ‘’变成一个空条件，通常查不到数据

所以最终页面显示出来的结果，实际上就是后半个 UNION SELECT 查出来的所有用户的用户名和密码。

3、错误型 SQL 注入

通过故意触发数据库错误，利用错误信息推测表名、列名或数据。

‘（单引号）： 闭合了原语句中 username = ‘ 的单引号。此时前面的条件变成了 username = ‘’（通常查不到数据，为假）

AND： 逻辑运算符。虽然前面为假，但数据库引擎在执行解析时，依然会去计算后面的条件

CONVERT(int, …) ：试图将这个包含版本信息的字符串强制转换为整数。 触发错误：在 SQL Server 中，将非数字字符串转换为整数会直接导致数据库抛出类型转换错误。

1=： 原本是为了与转换结果比对，但因为转换必然失败，所以查到这里的时候数据库已经崩溃并返回错误了

攻击者通过故意制造数据类型转换错误，让数据库把原本不应该显示的敏感信息（这里是数据库版本号）直接包含在报错信息中返回给前端，从而窃取信息。

4、盲注

无论输入什么，网页就只有两种反应：“正常”或者“异常”（比如永远显示“登陆失败”），我们通过“问问题”，来拼出真相，就叫盲注

第一部分：布尔型盲注（看页面反应猜真假）

database()： 用来获取当前网站使用的数据库名字的函数

SUBSTRING(…, 1, 1)： 意思是截取字符串的第 1 个字符，截取 1 位。所以这句话就是在拿数据库名字的第 1 个字母（也就是 t）

=’t’： 攻击者在猜测：“数据库名字的第一个字母，是不是字母 t？”

SELECT 1 WHERE …： 如果猜对了（是 t），就返回数字 1（代表真）；猜错了，什么都不返回（代表假）。

‘ AND … –： 把这段猜谜语的话拼接到原本的 SQL 里。

猜对后，可接着猜第二个字母

直到最终拼出完整的数据库

第二部分：时间盲注（看页面卡不卡）

无论你输入什么，网页永远显示“系统维护中”，用时间盲注

IF(条件, 动作A, 动作B)：这是 MySQL 的判断函数。意思是，如果条件成立，执行动作A；否则执行动作B。

SLEEP(5)：让数据库原地睡 5 秒（也就是卡顿 5 秒）。

​1=1​：这是一个永远成立的条件。

所以整句话的意思是：如果 1 等于 1（永远成立），那就让数据库卡 5 秒，否则立刻返回。

例：把 1=1 换成猜谜语的代码，如果页面卡了 5 秒才出来，说明数据库首字母真的是 ‘t’。如果秒出，说明不是 ‘t’

继续猜第二个字母、第三个字母，用这种“卡不卡”的时间差，硬生生把数据盲猜出来。

5、堆叠查询注入

允许多条 SQL 语句同时执行。

; （分号）： 在 SQL 里，分号代表“这一句写完了”。它硬生生地把原本的一句查询，截断成了第一句。

第一句： SELECT * FROM users WHERE username = ‘’ （查一下空用户名，没查到）
第二句： DROP TABLE users （把 users 表删了！）

特点：

  • 目的不同： 之前的注入都是为了“看”或“偷”数据。这个是为了“毁”数据
  • 前提条件： 这叫“堆叠注入”，并不是所有数据库都允许一次执行多条语句（比如 PHP+MySQL 默认通常不支持，但 SQL Server、PostgreSQL 或某些配置下是可以的）。
  • 删库跑路：攻击者一旦得手，轻则网站报错瘫痪，重则整个公司的核心数据直接蒸发。

7、Cookie 注入

利用修改浏览器存储的 Cookie 值进行注入。

正常请求查到了，就认为你登录了。Cookie 的值改成了’1’=‘1’

因为 ‘1’=’1’ 永远成立，这句话等同于“查出所有用户”

本周工作/学习总结：SQL注入漏洞梳理
一、 核心原理理解

一句话总结：应用程序没有把用户输入当成“数据”，而是直接拼接成了“代码”执行，导致网站分不清“普通信息”和“捣乱命令”。

二、 主要攻击类型与危害（按目的分类）
  1. 逻辑绕过类（基础型 / Cookie注入）
    手法：利用 ‘ OR ‘1’=’1 等万能条件，或通过注释符 – 截断密码验证。
    危害：无需正确的账号密码即可登录，甚至直接获取管理员权限。
    特点：注入点不局限于输入框，Cookie 里的 session_id 等请求头同样可能中招。
  2. 数据窃取类（UNION / 报错注入）
    手法：UNION 合并查询直接回显敏感数据；报错注入利用类型转换错误让版本号等信息在报错信息中泄露。
    危害：直接泄露数据库版本、表名、用户账号密码等敏感信息。
  3. 无回显猜解类（盲注）
    手法：布尔盲注（猜对了页面有微小变化）；时间盲注（猜对了利用 SLEEP(5) 卡顿5秒）。
    危害：即使网站不显示任何错误或数据，攻击者也能靠脚本逐字猜出整个数据库。
  4. 毁灭与提权类（堆叠注入 / 命令执行）
    手法：利用分号 ; 追加恶意指令。如 DROP TABLE 直接删库；利用 SQL Server 的 xp_cmdshell 绕过数据库执行系统命令。
    危害：最致命。从单纯的数据泄露升级为服务器被接管、核心数据被销毁。
三、 学习感悟与防御思路

这周最大的感悟是：永远不要信任用户的任何输入。

要防范此类漏洞，必须在开发中严格使用参数化查询（预编译） ；同时，数据库账号必须遵循最小权限原则（绝不给网站连库账号分配删表和执行系统命令的权限），并关闭生产环境的前端详细报错。
